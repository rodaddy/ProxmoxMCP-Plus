# MCP 2026-07-28 (SDK v2) additive path

**Truth state: WRITTEN, 2026-08-09. Not deployed.** Nothing in this document
has run on CT 215. Every claim below was verified on a local macOS dev machine
against a stub Proxmox API. Program: MCP 2026-07-28 cutover
(map `rodaddy/development#104`, ticket dev#111).

## What this adds

A second, parallel MCP server that speaks the 2026-07-28 stateless HTTP wire:

| | v1 (live today) | v2 (this change) |
|---|---|---|
| module | `proxmox_mcp.server` | `proxmox_mcp.server_v2` |
| SDK | `mcp>=1.8.0,<2.0.0` (observed 1.29.0) | `mcp==2.0.0` |
| entry | `FastMCP` | `MCPServer` |
| env | the existing venv | a separate `.venv-v2` |
| tools | full surface incl. writes | six read-only verbs only |

The v1 module is **not modified**. The only edit to a shared file is
`src/proxmox_mcp/__init__.py`, made lazy so that importing `server_v2` no
longer drags in `mcp.server.fastmcp` (which does not exist in 2.x). The v1
public API `from proxmox_mcp import ProxmoxMCPServer` still resolves
identically.

## Why two environments and not one

`proxmox_mcp.server` imports `mcp.server.fastmcp`. That module was removed in
SDK 2.x with no alias and no deprecation shim, so **the two SDK majors cannot
coexist in one environment**. The `[v2]` extra therefore deliberately
conflicts with the base pin, and `overrides-v2.txt` lifts the ceiling for the
v2 environment only.

Installing the `[v2]` extra into the v1 environment would break the running
server. Build it separately:

```
uv venv .venv-v2
uv pip install --python .venv-v2 -e ".[v2]" --override overrides-v2.txt
```

## Strictness: the part that is easy to get wrong

The SDK's derived schema is permissive. Verified live on `mcp==2.0.0`
(2026-08-09): calling a two-argument tool with an extra `BOGUS` key returned
the correct answer with `is_error=False` — **the undeclared parameter was
silently dropped**. The v1→v2 bump does not fix this.

Enforcement needs BOTH halves, and this was proven by mutation:

1. `additionalProperties: false` on the advertised schema — **advertisement only**.
2. `extra="forbid"` on the pydantic argument model — **this is what rejects**.

Applying only (1) leaves the server advertising a contract it does not honour.
The `--mutate advertise-only` run of the done-means script exists specifically
to demonstrate that failure mode.

`proxmox_mcp.strictness` reaches through `MCPServer._tool_manager`, a private
surface, because 2.0.0 exposes no author-facing hook. That is why `mcp` is
pinned **exactly**, and why the module raises `StrictnessSurfaceError` rather
than degrading quietly if the surface moves.

Wire shape is preserved: arguments stay flat (`{"node": "proxmox01"}`), never
nested under `args`.

## Scope: read-only

Only `get_nodes`, `get_node_status`, `get_vms`, `get_containers`,
`get_storage`, `get_cluster_status` are registered. Write verbs
(`create_vm`, `delete_container`, `execute_vm_command`, …) are deliberately
absent; a new wire revision is not the place to re-expose cluster mutation.
`READ_ONLY_TOOLS` is asserted by both the test suite and the done-means gate,
so adding a write verb fails the gate rather than shipping quietly.

## Verifying

```
./.venv-v2/bin/python scripts/done_means_v2.py          # expect ALL GREEN, exit 0
./.venv-v2/bin/python -m pytest tests/test_strictness.py -p anyio
```

Prove the gate can fail before trusting it — each of these MUST exit non-zero:

```
./.venv-v2/bin/python scripts/done_means_v2.py --mutate no-strict
./.venv-v2/bin/python scripts/done_means_v2.py --mutate advertise-only
./.venv-v2/bin/python scripts/done_means_v2.py --mutate break-old-path
```

No real Proxmox cluster is contacted: the server under test is built with
`build_server(proxmox_api=StubProxmoxAPI())`, and the stub raises
`ForbiddenWriteError` on `post`/`put`/`delete`/`create`.

## Deployment (NOT done in this change)

Deployment to CT 215 is a separate, operator-gated step. When it happens:

- CT 215 currently runs `proxmox-mcp.service` from `/opt/proxmox-mcp`
  (`ExecStart=/opt/proxmox-mcp/.venv/bin/python -m proxmox_mcp.server`,
  `transport: STREAMABLE`, `0.0.0.0:8000`). That unit and that venv are the
  v1 path — **leave both alone**.
- Run v2 as a SECOND unit with its OWN venv and its OWN port. Do not point the
  existing unit at `server_v2`.
- Bind the literal address. Never the name `localhost`: on macOS it resolves
  `::1` first and the server binds IPv6-only, so every `127.0.0.1` client gets
  `ECONNREFUSED` that reads as "server down". First diagnostic on a refusal:
  `lsof -nP -iTCP:<port> -sTCP:LISTEN`.
- Probe readiness with the operation you intend to use. A GET on the MCP
  endpoint opens a long-lived SSE stream and will hang, making a healthy
  server look unreachable.

## Rollback

The way back, in order of cost:

1. **Nothing deployed yet** — this branch is additive and unmerged; not
   merging it is a complete rollback with no residue.
2. **Merged, not deployed** — the v1 unit on CT 215 never referenced
   `server_v2`, so a merged-but-undeployed branch changes no running
   behaviour. Verify with `systemctl cat proxmox-mcp.service` still naming
   `-m proxmox_mcp.server`.
3. **v2 deployed alongside v1** — `systemctl stop <v2-unit>`. The v1 unit is a
   separate process with a separate venv and was never modified, so stopping
   v2 returns the box to exactly its current state. Confirm v1 health from the
   live object's own signal, not from config on disk.

The single shared-file edit (`__init__.py`) is behaviour-preserving for v1 and
is covered by the done-means old-path control clause, which runs before AND
after the v2 checks.
